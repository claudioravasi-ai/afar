REGLAS DE SEGURIDAD PARA LA REALTIME DATABASE DE AFAAR
=====================================================

Firebase crea la base en "modo de prueba", con reglas que dejan leer y escribir
a cualquiera hasta una fecha de vencimiento. Eso sirve para probar la app, pero
NO para trabajar con datos reales de pacientes.

Pegá estas reglas en:
   Consola de Firebase -> Build -> Realtime Database -> pestaña "Reglas"

--------------------------------------------------------------------
OPCIÓN A — mínima, mientras se prueba con datos ficticios
--------------------------------------------------------------------
{
  "rules": {
    "afar": {
      ".read": true,
      ".write": true,
      ".indexOn": ["fecha", "ownerUid"]
    }
  }
}

Cualquiera que conozca la URL de la base puede leer y escribir. Usala sólo con
datos de prueba y cambiala antes del uso asistencial.


--------------------------------------------------------------------
OPCIÓN B — recomendada: exige autenticación de Firebase
--------------------------------------------------------------------
Requiere activar Authentication en la consola (por ejemplo, el proveedor
"Anónimo" o "Correo/contraseña") y que la app inicie sesión en Firebase.
Si querés dar este paso, avisá y se agrega el inicio de sesión de Firebase
a la aplicación.

{
  "rules": {
    "afar": {
      ".read": "auth != null",
      ".write": "auth != null",
      "usuarios": {
        "$uid": {
          ".write": "auth != null"
        }
      },
      "fichas": {
        ".indexOn": ["ownerUid", "fecha"]
      },
      "pacientes": {
        ".indexOn": ["ownerUid"]
      }
    }
  }
}


--------------------------------------------------------------------
RECOMENDACIONES ADICIONALES
--------------------------------------------------------------------
1. Restringí la clave de API por dominio en:
   Google Cloud Console -> APIs y servicios -> Credenciales -> Restricciones
   de referente HTTP. Agregá sólo el dominio donde publiques la app.

2. Activá las copias de seguridad automáticas de la Realtime Database
   (requiere el plan Blaze) y, además, descargá el respaldo JSON desde
   Coordinación -> Nube y respaldos con regularidad.

3. Elegí la región de la base al crearla; después no se puede cambiar.
   Para Argentina conviene southamerica-east1 o us-central1.

4. Los datos de salud están alcanzados por la Ley 25.326 de Protección de
   Datos Personales y por la Ley 26.529 de Derechos del Paciente. La historia
   clínica debe conservarse un mínimo de diez años desde la última actuación.


--------------------------------------------------------------------
RAMAS DE LA BASE
--------------------------------------------------------------------
Todo cuelga de "afar". Las colecciones normales (usuarios, pacientes, fichas,
instituciones, obrasSociales, catalogoExtra, config, auditoria, mensajes,
fiscal, envios) las escucha cada dispositivo en vivo y las guarda enteras en
el equipo.

"afar/archivos" es distinta y no hay que agregarla a ninguna suscripcion: son
los documentos enviados a contaduria y las fotos del parte quirurgico. Pesan
cientos de KB cada uno y se leen de a uno, cuando alguien abre un envio. Si se
escucharan como el resto, un solo parte quirurgico fotografiado llenaria el
almacenamiento local de todos los telefonos.

Con la Opcion A no hace falta hacer nada: "afar" ya cubre a "archivos". Si
alguna vez se pasa a la Opcion B, "archivos" tiene que quedar con las mismas
reglas que el resto, y conviene ademas limitar el tamano:

  "archivos": {
    "$id": {
      ".read": "auth != null",
      ".write": "auth != null && newData.child('datos').val().length < 12000000"
    }
  }

Ojo: los envios a contaduria contienen nombre y DNI del paciente, la cirugia y
el diagnostico. Es una cesion deliberada, que dispone el profesional tratante
para facturar y para responder auditorias medicas, pero significa que la rama
"envios" y la rama "archivos" son las mas sensibles de la base. Son un motivo
mas para cerrar las reglas antes del primer paciente real.
